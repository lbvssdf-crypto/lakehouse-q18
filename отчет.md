## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему выбран |
| --- | --- | --- |
| Silo (S3-совместимое хранилище) | Файлы Iceberg, бакет warehouse; контейнер lakehouse-minio. | Работает через S3-совместимый API, поэтому данные хранятся локально без облачного сервиса. |
| PostgreSQL | Служебная база Lakekeeper; контейнер lakehouse-pg. | Подходит для хранения служебной базы каталога и быстро запускается локально в Docker. |
| Lakekeeper | Iceberg REST Catalog, warehouse demo. | Позволяет управлять Iceberg-таблицами отдельно от Trino и объектного хранилища. |
| Trino 476 | SQL-движок, каталоги tpch и lakekeeper. | Позволяет работать с Iceberg через SQL, создавать таблицы и выполнять аналитические запросы. |
| Metabase | BI-инструмент для просмотра Bronze и Gold. | Подключается к Trino и показывает результаты запросов в браузере. |

Для выполнения запросов и фиксации времени их работы использовался DBeaver на Windows. Он запускался отдельно от Docker.

### Скрипты запуска сервисов

Ниже приведены команды первоначального развёртывания. Пароли и ключи заменены переменными, чтобы не публиковать их в отчёте. Ранее созданные контейнеры запускаются командой docker start — повторять docker run не нужно.

```powershell
# Silo / MinIO-совместимое S3-хранилище

docker run -d --name lakehouse-minio -p 9000:9000 -p 9001:9001 `
  -e MINIO_ROOT_USER=$env:S3_USER -e MINIO_ROOT_PASSWORD=$env:S3_PASSWORD `
  -v minio-data:/data pgsty/silo:RELEASE.2026-11-12T00-00-00Z `
  server /data --console-address ':9001'
# PostgreSQL

docker run -d --name lakehouse-pg -p 5432:5432 `
  -e POSTGRES_PASSWORD=$env:DB_PASSWORD -v pg-data:/var/lib/postgresql/data postgres:17
# Первоначальная миграция Lakekeeper

docker run --rm `
  -e LAKEKEEPER__PG_ENCRYPTION_KEY=$env:LK_KEY `
  -e "LAKEKEEPER__PG_DATABASE_URL_READ=$env:LK_DB_URL" `
  -e "LAKEKEEPER__PG_DATABASE_URL_WRITE=$env:LK_DB_URL" `
  quay.io/lakekeeper/catalog:latest-main migrate
# Lakekeeper (сервер после миграции)

docker run -d --name lakekeeper -p 8181:8181 `
  -e LAKEKEEPER__PG_ENCRYPTION_KEY=$env:LK_KEY `
  -e "LAKEKEEPER__PG_DATABASE_URL_READ=$env:LK_DB_URL" `
  -e "LAKEKEEPER__PG_DATABASE_URL_WRITE=$env:LK_DB_URL" `
  quay.io/lakekeeper/catalog:latest-main serve
# Trino: каталог Iceberg лежит в локальной папке catalog

docker run -d --name trino -p 8080:8080 `
  -v "${PWD}\catalog:/etc/trino/catalog" trinodb/trino:476
# Metabase: локальная база настроек в Docker volume

docker run -d --name lakehouse-metabase -p 3000:3000 `
  -v metabase-data:/metabase-data `
  -e MB_DB_FILE=/metabase-data/metabase.db metabase/metabase:latest
```

После миграции Lakekeeper был инициализирован через bootstrap. В Silo создан бакет warehouse, а в Lakekeeper зарегистрирован warehouse demo. Локальные ключи доступа в отчёт не включены.

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос делает |
| --- | --- | --- |
| customer | custkey, name | Связь customer → orders по custkey; вывод имени и идентификатора. |
| orders | orderkey, custkey, orderdate, totalprice | Связь с заказом и позициями; вывод даты, суммы; сортировка по totalprice DESC. |
| lineitem | orderkey, quantity | SUM(quantity) по заказу, HAVING SUM(quantity) > 300. |

Q18 на исходных таблицах; условие строгое (> 300), результат сортируется по стоимости и ограничивается сотней строк.

```sql
WITH large_orders AS (
  SELECT orderkey, SUM(quantity) AS total_quantity
  FROM tpch.sf1.lineitem
  GROUP BY orderkey HAVING SUM(quantity) > 300
)
SELECT c.name, c.custkey, o.orderkey, o.orderdate,
       o.totalprice, l.total_quantity
FROM tpch.sf1.customer c
JOIN tpch.sf1.orders o ON c.custkey = o.custkey
JOIN large_orders l ON o.orderkey = l.orderkey
ORDER BY o.totalprice DESC, o.orderdate, o.orderkey
LIMIT 100;
```

## 4. Медальон — решения по каждому слою

В каталоге lakekeeper созданы отдельные схемы bronze, silver и gold. Для рабочих таблиц использован Parquet; свойство записи write.parquet.compression-codec = zstd проверено для всех восьми таблиц. Партиционирование не задавалось: при объёме SF1 от него не ожидалось заметной пользы, зато усложнилась бы структура файлов.

### Bronze (сырой)

Для Bronze я оставил исходные столбцы без изменения. Parquet и ZSTD подходят для хранения большого набора строк, а партиционирование для SF1 не требуется.

| Таблица | Колонки | Строк | МиБ | Формат | Сжатие | Партиц. | Обоснование |
| --- | --- | --- | --- | --- | --- | --- | --- |
| customer | Все исходные | 150 000 | 7,8 | Parquet | ZSTD | Нет | Сохранение полного источника клиентов. |
| orders | Все исходные | 1 500 000 | 35,0 | Parquet | ZSTD | Нет | Полный источник заказов для связей. |
| lineitem | Все исходные | 6 001 215 | 147,2 | Parquet | ZSTD | Нет | Позиции заказов для последующей агрегации. |

Сначала создаются схемы Bronze, Silver и Gold. Затем команды CREATE TABLE ... AS SELECT (CTAS) копируют исходные данные tpch.sf1 в Iceberg-таблицы Bronze без удаления столбцов.

```sql
-- Схемы: сырой, очищенный и аналитический уровни
CREATE SCHEMA IF NOT EXISTS lakekeeper.bronze;
CREATE SCHEMA IF NOT EXISTS lakekeeper.silver;
CREATE SCHEMA IF NOT EXISTS lakekeeper.gold;
-- Сырые данные клиентов (полная копия колонок из TPC-H)
CREATE TABLE lakekeeper.bronze.customer WITH (format='PARQUET') AS
SELECT * FROM tpch.sf1.customer;
-- Все заказы для соединения с клиентами
CREATE TABLE lakekeeper.bronze.orders WITH (format='PARQUET') AS
SELECT * FROM tpch.sf1.orders;
-- Позиции заказов для суммирования количества quantity
CREATE TABLE lakekeeper.bronze.lineitem WITH (format='PARQUET') AS
SELECT * FROM tpch.sf1.lineitem;
-- Контроль объёмов исходных таблиц
SELECT (SELECT COUNT(*) FROM lakekeeper.bronze.customer) AS customers,
 (SELECT COUNT(*) FROM lakekeeper.bronze.orders) AS orders,
 (SELECT COUNT(*) FROM lakekeeper.bronze.lineitem) AS lineitems;
```

### Silver (очищенный)

В Silver оставлены поля, используемые в Q18: благодаря этому таблицы меньше исходных. Parquet и ZSTD сохранены для единообразия; по тем же причинам таблицы не партиционировались.

| Таблица | Колонки | Строк | МиБ | Формат | Сжатие | Партиц. | Обоснование |
| --- | --- | --- | --- | --- | --- | --- | --- |
| customer_clean | custkey, name | 150 000 | 0,3 | Parquet | ZSTD | Нет | Удалены NULL, TRIM(name). |
| orders_clean | orderkey, custkey, orderdate, totalprice, order_year | 1 500 000 | 13,4 | Parquet | ZSTD | Нет | Проверка ключей и цены; добавлен год. |
| lineitem_clean | orderkey, quantity | 6 001 215 | 6,8 | Parquet | ZSTD | Нет | Только нужные поля и qty > 0. |
| large_orders | orderkey, total_quantity | 57 | 0,00* | Parquet | ZSTD | Нет | Агрегат по orderkey с SUM > 300. |

Количество строк всех четырёх таблиц Silver подтверждено запросом COUNT(*): 150 000, 1 500 000, 6 001 215 и 57 соответственно. * Значение 0,00 МиБ возникает из-за округления небольшого размера таблицы до двух знаков после запятой.

Преобразования Silver:

```sql
-- Очистка и нормализация клиента
CREATE TABLE lakekeeper.silver.customer_clean WITH (format='PARQUET') AS
SELECT custkey, TRIM(name) AS name FROM lakekeeper.bronze.customer
WHERE custkey IS NOT NULL AND name IS NOT NULL;
-- Обогащение заказа годом (order_year)
CREATE TABLE lakekeeper.silver.orders_clean WITH (format='PARQUET') AS
SELECT orderkey, custkey, orderdate, totalprice, YEAR(orderdate) AS order_year
FROM lakekeeper.bronze.orders
WHERE orderkey IS NOT NULL AND custkey IS NOT NULL
  AND orderdate IS NOT NULL AND totalprice IS NOT NULL AND totalprice >= 0;
-- Выбор нужных позиций и подготовка крупных заказов
CREATE TABLE lakekeeper.silver.lineitem_clean WITH (format='PARQUET') AS
SELECT orderkey, quantity FROM lakekeeper.bronze.lineitem
WHERE orderkey IS NOT NULL AND quantity IS NOT NULL AND quantity > 0;
CREATE TABLE lakekeeper.silver.large_orders WITH (format='PARQUET') AS
SELECT orderkey, SUM(quantity) AS total_quantity
FROM lakekeeper.silver.lineitem_clean
GROUP BY orderkey HAVING SUM(quantity) > 300;
```

Количество строк Silver проверено отдельным запросом COUNT(*). Результат совпал с данными, приведёнными в таблице выше: customer_clean — 150 000, orders_clean — 1 500 000, lineitem_clean — 6 001 215, large_orders — 57.

```sql
SELECT
  (SELECT COUNT(*) FROM lakekeeper.silver.customer_clean) AS customers_clean,
  (SELECT COUNT(*) FROM lakekeeper.silver.orders_clean) AS orders_clean,
  (SELECT COUNT(*) FROM lakekeeper.silver.lineitem_clean) AS lineitems_clean,
  (SELECT COUNT(*) FROM lakekeeper.silver.large_orders) AS large_orders;
-- Условие Q18: минимальное количество в отобранных заказах
SELECT COUNT(*) AS large_orders_count,
       MIN(total_quantity) AS min_quantity
FROM lakekeeper.silver.large_orders;
```

### Gold (витрина)

Gold хранит только готовый результат Q18. Таблица небольшая, поэтому отдельные партиции не нужны; формат Parquet и кодек ZSTD оставлены такими же, как в остальных слоях.

| Таблица | Колонки | Строк | МиБ | Формат | Сжатие | Партиц. | Обоснование |
| --- | --- | --- | --- | --- | --- | --- | --- |
| q18_top100 | name, custkey, orderkey, orderdate, totalprice, total_quantity | 57 | 0,00* | Parquet | ZSTD | Нет | Готовый топ заказов по сумме, с qty > 300. |

В Gold соединяются очищенные клиенты, заказы и таблица large_orders. Запрос выбирает до 100 самых дорогих заказов; на SF1 условию соответствуют 57 заказов. При просмотре таблицы сортировка задаётся отдельным ORDER BY.

```sql
CREATE SCHEMA IF NOT EXISTS lakekeeper.gold;
CREATE TABLE lakekeeper.gold.q18_top100 WITH (format='PARQUET') AS
SELECT c.name, c.custkey, o.orderkey, o.orderdate,
       o.totalprice, l.total_quantity
FROM lakekeeper.silver.customer_clean AS c
JOIN lakekeeper.silver.orders_clean AS o ON c.custkey = o.custkey
JOIN lakekeeper.silver.large_orders AS l ON o.orderkey = l.orderkey
ORDER BY o.totalprice DESC, o.orderdate ASC, o.orderkey ASC
LIMIT 100;
-- Проверка результата и условия крупного заказа
SELECT COUNT(*) AS total_rows FROM lakekeeper.gold.q18_top100;
SELECT MIN(total_quantity) AS min_quantity,
       MAX(total_quantity) AS max_quantity
FROM lakekeeper.gold.q18_top100;
-- Просмотр готовой витрины
SELECT * FROM lakekeeper.gold.q18_top100
ORDER BY totalprice DESC, orderdate, orderkey;
```

Результат содержит 57 строк при LIMIT 100; все выведенные заказы удовлетворяют количеству > 300. Размер 0,00 МиБ — округление до двух знаков.

## 5. Тесты производительности

Производительность проверялась в двух экспериментах. В первом сравнивались два полных набора Bronze (customer, orders и lineitem) в Parquet с кодеками GZIP и ZSTD. Во втором сравнивались форматы Parquet и ORC на одинаковых 6 001 215 строках lineitem. Для измерения времени использовался DBeaver, для размера — метаданные файлов Iceberg.

### Сравнение GZIP и ZSTD для полного Bronze

| Сжатие Bronze | Q18, медиана 3 запусков, с | Запись Bronze, с | Размер полного Bronze, МиБ | Твой вывод (что лучше и почему) |
| --- | --- | --- | --- | --- |
| GZIP (Parquet) | 2,212 | 33,698 | 184,9 | Меньший размер файлов, но запись и выполнение Q18 занимают больше времени. |
| ZSTD (Parquet) | 1,821 | 16,317 | 190,1 | Быстрее запись и Q18; увеличение размера на 5,2 МиБ приемлемо для этой работы. |

Суммарное время записи — сумма времени создания трёх таблиц одного варианта. Для GZIP: 4,698 + 12,000 + 17,000 = 33,698 с; для ZSTD: 1,707 + 4,654 + 9,956 = 16,317 с. Общий размер измерен по метаданным активных файлов всех трёх таблиц: 184,9 МиБ (GZIP) и 190,1 МиБ (ZSTD). Время Q18 — медиана трёх запусков на полном наборе соответствующего кодека.

Для бенчмарка рабочие таблицы Bronze не менялись: копии customer, orders и lineitem размещены в lakekeeper.benchmark. Это исключает риск изменения Gold-витрины. Для эксперимента использовался один масштаб TPC-H SF1, а кодек задавался перед CTAS.

#### Создание и проверка копий полного Bronze

Для customer и orders созданы копии в обоих кодеках. Копии lineitem использованы из первого эксперимента. Кодеки GZIP/ZSTD проверены в свойствах Iceberg-таблиц. Ниже приведены команды создания всех новых копий; перед каждым блоком устанавливается нужная настройка сессии Trino.

```sql
-- Кодек для первой пары копий
SET SESSION lakekeeper.compression_codec = 'GZIP';
CREATE TABLE lakekeeper.benchmark.customer_parquet_gzip
WITH (format='PARQUET') AS
SELECT * FROM lakekeeper.bronze.customer;
CREATE TABLE lakekeeper.benchmark.orders_parquet_gzip
WITH (format='PARQUET') AS
SELECT * FROM lakekeeper.bronze.orders;

-- Вторая пара копий
SET SESSION lakekeeper.compression_codec = 'ZSTD';
CREATE TABLE lakekeeper.benchmark.customer_parquet_zstd
WITH (format='PARQUET') AS
SELECT * FROM lakekeeper.bronze.customer;
CREATE TABLE lakekeeper.benchmark.orders_parquet_zstd
WITH (format='PARQUET') AS
SELECT * FROM lakekeeper.bronze.orders;
```

В таблице отражены размеры файлов данных без служебных метаданных Iceberg.

```sql
WITH sizes AS (
  SELECT 'GZIP' AS codec, 'customer' AS tbl, SUM(file_size_in_bytes) AS bytes
  FROM lakekeeper.benchmark."customer_parquet_gzip$files"
  UNION ALL SELECT 'GZIP', 'orders', SUM(file_size_in_bytes)
  FROM lakekeeper.benchmark."orders_parquet_gzip$files"
  UNION ALL SELECT 'GZIP', 'lineitem', SUM(file_size_in_bytes)
  FROM lakekeeper.benchmark."lineitem_parquet_gzip$files"
  UNION ALL SELECT 'ZSTD', 'customer', SUM(file_size_in_bytes)
  FROM lakekeeper.benchmark."customer_parquet_zstd$files"
  UNION ALL SELECT 'ZSTD', 'orders', SUM(file_size_in_bytes)
  FROM lakekeeper.benchmark."orders_parquet_zstd$files"
  UNION ALL SELECT 'ZSTD', 'lineitem', SUM(file_size_in_bytes)
  FROM lakekeeper.benchmark."lineitem_parquet_zstd$files"
)
SELECT codec,
  ROUND(SUM(CASE WHEN tbl='customer' THEN bytes ELSE 0 END)/1048576.0,2) AS customer_mib,
  ROUND(SUM(CASE WHEN tbl='orders' THEN bytes ELSE 0 END)/1048576.0,2) AS orders_mib,
  ROUND(SUM(CASE WHEN tbl='lineitem' THEN bytes ELSE 0 END)/1048576.0,2) AS lineitem_mib,
  ROUND(SUM(bytes)/1048576.0,2) AS total_bronze_mib
FROM sizes GROUP BY codec ORDER BY codec;
```

### 6.1. Понять и объяснить

| Вопрос | Ответ |
| --- | --- |
| Зачем нужны большие данные и Lakehouse вместо обычной БД/хранилища? | В Lakehouse файлы данных хранятся отдельно от метаданных таблиц и SQL-движка. Поэтому одни и те же данные можно обрабатывать разными инструментами, а Iceberg позволяет менять схему и обращаться к предыдущим версиям. Для небольшой транзакционной базы обычная СУБД проще; Lakehouse полезнее, когда нужно хранить и анализировать большие объёмы данных. |
| Пример Schema Evolution на Silver: что произошло? | В тестовой Iceberg-таблице с пятью клиентами добавлен столбец customer_status. Затем он переименован в customer_segment командой RENAME COLUMN. Повторный DESCRIBE показал новое имя вместо старого. Все пять исходных строк сохранились; значения новой колонки равны NULL. |
| Пример восстановления данных из снапшота (Time Travel) | Для silver.time_travel_demo создана версия с Ivan и Anna, затем добавлен Petr. Через FOR VERSION AS OF прочитана прежняя версия, а rollback_to_snapshot вернул два исходных имени как текущее состояние. |

В таблице schema_evolution_final_demo сначала добавлен столбец customer_status, затем выполнено переименование в customer_segment. Проверки DESCRIBE до и после переименования подтвердили изменение схемы. SELECT показал, что пять исходных клиентов остались в таблице, а новая колонка содержит NULL.

```sql
-- Шаг 1. Создать новую таблицу с пятью клиентами (отдельная демонстрация)
CREATE TABLE lakekeeper.silver.schema_evolution_final_demo
WITH (format='PARQUET') AS
SELECT custkey, name
FROM lakekeeper.silver.customer_clean
LIMIT 5;
-- Шаг 2. Добавляем новый столбец без перезаписи старых строк
ALTER TABLE lakekeeper.silver.schema_evolution_final_demo
ADD COLUMN customer_status VARCHAR;
-- Доказательство состояния после ADD COLUMN
DESCRIBE lakekeeper.silver.schema_evolution_final_demo;
-- Шаг 3. Меняем имя колонки в метаданных Iceberg
ALTER TABLE lakekeeper.silver.schema_evolution_final_demo
RENAME COLUMN customer_status TO customer_segment;
-- Доказательство, что customer_status больше нет
DESCRIBE lakekeeper.silver.schema_evolution_final_demo;
-- Шаг 4. Старые строки сохранились, новое поле пока NULL
SELECT custkey, name, customer_segment
FROM lakekeeper.silver.schema_evolution_final_demo;
```

Time Travel: первый снапшот хранит две строки Ivan и Anna; вставка Petr создаёт вторую версию. FOR VERSION AS OF читает первую версию без изменения текущей, а rollback_to_snapshot возвращает первую версию в качестве текущей.

```sql
-- Создание независимой тестовой таблицы
CREATE TABLE lakekeeper.silver.time_travel_demo
WITH (format='PARQUET') AS
SELECT * FROM (VALUES (1, 'Ivan'), (2, 'Anna')) AS t(id, name);
-- Состояние до изменения: две строки
SELECT * FROM lakekeeper.silver.time_travel_demo ORDER BY id;
-- ID исходного снапшота и время создания
SELECT snapshot_id, committed_at, operation
FROM lakekeeper.silver."time_travel_demo$snapshots"
ORDER BY committed_at;
-- Меняем данные: теперь три строки
INSERT INTO lakekeeper.silver.time_travel_demo VALUES (3, 'Petr');
SELECT * FROM lakekeeper.silver.time_travel_demo ORDER BY id;
-- Смотрим историю двух снапшотов
SELECT snapshot_id, committed_at, operation
FROM lakekeeper.silver."time_travel_demo$snapshots"
ORDER BY committed_at;
-- Читаем старую версию (ID получен в эксперименте)
SELECT * FROM lakekeeper.silver.time_travel_demo
FOR VERSION AS OF 2175375528739687787 ORDER BY id;
-- Восстанавливаем первый снапшот как текущий
ALTER TABLE lakekeeper.silver.time_travel_demo
EXECUTE rollback_to_snapshot(2175375528739687787);
-- Проверяем: снова Ivan и Anna
SELECT * FROM lakekeeper.silver.time_travel_demo ORDER BY id;
```
